# Prospective analysis protocol: matched frozen-JEPA control

This protocol was written on 2026-09-19 before the fresh full-budget endpoints were analyzed. It applies to `runs/revision/matched` only. Historical gate results and the native-grid-policy sensitivity use separate labels and output directories.

## Question, interventions and endpoints

Within each **fixed fitted encoder, predictor and head checkpoint**, how does final real-gate behavior change when the training transition source changes from learned latent dynamics to exact simulator transitions, and when learned reward/termination signals are subsequently replaced by true signals?

The planned primary design is three model checkpoints (model seeds 0, 1, 2), five policy seeds per checkpoint (0–4), and three arms per policy seed, for 45 training runs. Each run requests 150 updates × 512 starts × 16 steps = 1,228,800 training transitions. `learned` uses the frozen predictor and learned task heads; `oracle_heads` uses exact simulator transitions re-encoded by the same encoder, with the same learned heads; `oracle_true` uses exact re-encoded transitions with true reward/termination. Actor, optimizer, start-state mixture, context, training update count and evaluation keys are intended to match.

The two predeclared main endpoints are **walls passed per real episode** and **survival probability to the 128-step cap**. A death on step 128 remains a death: survival is derived from episode return 0 versus −1, not from duration. Discovery (survival strictly above 50%) is secondary descriptive information. Training loss and best intermediate policies are not selection criteria.

The predeclared contrasts are:

1. `oracle_heads − learned`: change the transition source while retaining learned task heads.
2. `oracle_true − oracle_heads`: change task signals under exact transitions.
3. `oracle_true − learned`: the complete training-pipeline difference.

All signs are target minus reference; larger is better for both endpoints. The first contrast also changes support after true terminal events: exact-simulator arms freeze terminal states, while `oracle_heads` continues to apply its learned signals there. This is a named limitation, not a pure dynamics-only intervention. Report the logged postterminal alive mass and reward alongside this comparison.

## Eligibility and pairing checks

Only `final.json` from a full requested budget is eligible. `budget_complete` must be true, completed/requested/config updates must all equal 150, and final transition count and ledger updates must agree. No best checkpoint is read. Model/policy seed, arm, evaluation seed and checkpoint identity must agree across final, config and episode metadata. Final scalar metrics are independently recomputed from `episodes.npz`; discrepancies invalidate the run.

The analysis accepts only **complete three-arm blocks for the same model seed and policy seed**. If an arm is absent, incomplete, duplicated or invalid, that entire seed block is excluded from provisional comparisons. This prevents arm means from silently using different seed populations. Nonfinite training losses or other required training diagnostics are reported as numerical failures; the corresponding seed remains unresolved in the planned denominator. The publication analysis is marked complete only when every planned block passes. An incomplete artifact sync is reported as incomplete, never treated as a zero.

For every block, require matching semantic hashes of `starts.npz:indices`, model SHA256, training-data archive SHA256, source-content identities, all recorded matching training hyperparameters, policy parameter count, final evaluation seed and evaluation episode count. Integer start arrays are hashed with canonical integer representation and shape, so NPZ compression metadata does not affect the test. Data-byte hash mismatches require an explicit provenance investigation rather than silent aliasing. The current design puts a given fixed checkpoint's three arms on the same dataset copy.

Within each model checkpoint, dataset hash, evaluation key, episode count, source version, policy architecture and training protocol must also match across policy seeds. This is needed for jointly resampling episode slots across policies. The episode indices are the ordered slots generated by the common evaluator and fixed PRNG key; the archive does not contain separately named episode IDs. Source hashes verify that the evaluator implementation matches. If final policy binaries are locally available, their SHA256 must match the saved final metadata; absence is recorded and does not replace outcome verification.

## Estimands and uncertainty

Show every model seed separately. Within a fixed model, first compute each paired policy-seed difference from its per-episode outcomes, then average those policy differences with equal weights. Report the individual differences and arm endpoints. The main interval is a 95% percentile bootstrap that resamples the **paired policy seeds** within this fixed checkpoint, conditional on the saved evaluation set, using 10,000 draws and deterministic analysis seed 7341. With only five policy seeds it is a coarse descriptive interval. With one eligible seed, no policy-training uncertainty interval is reported.

Additionally compute conditional evaluation intervals by resampling paired episode slots while keeping fitted policies fixed. For the average over policy seeds, resample the same slot jointly across all policies because their evaluation keys are shared. For each individual policy contrast, also report its paired-episode interval. These intervals answer a different question from the policy-seed bootstrap: they quantify evaluation variation conditional on fitted policies and do not substitute for model-training or policy-training uncertainty. Do not count 5 × 256 episode outcomes as independent model or policy replications.

Across the three fixed model fits, report the three within-model effects, their equal-model descriptive mean, and their minimum/maximum range. Do not produce a model-family confidence interval or turn 15 policy pairs into 15 independent model fits. The limited sample of three fits does not justify a confident claim about the entire model family. No family-level hierarchical bootstrap is used.

All intervals are unadjusted descriptive 95% intervals across two endpoints, three contrasts and three fixed checkpoints. Do not make a significance-filtered headline or select the most favorable metric, seed, policy, contrast or model. Show incomplete/invalid runs and pairing failures explicitly. Mechanistic interpretation must remain tied to the precise intervention and its terminal-state semantics.

## Separate sensitivity analysis

The native-grid policy experiment, if run, uses three policy seeds × three model seeds × three arms. Analyze it separately with `--policy-seeds 0,1,2 --label native-grid`; never pool its endpoints or bootstrap samples with the MLP primary analysis. The altered policy inductive bias answers whether the observation-to-policy interface constrains behavior; it is not additional replication of the primary policy class. Final-budget and pairing rules remain the same.

## Reproduction and outputs

The analysis module imports only standard Python libraries and NumPy. It does not import training code, JAX or the model checkpoint, mutate any run artifact, run any environment, or select checkpoints.

```bash
python -m studies.revision.analyze_matched --self-test
python -m studies.revision.analyze_matched \
  --runs-root runs/revision/matched \
  --output-dir output/revision/matched-analysis \
  --require-complete
```

Outputs are `publication.json`, `table.md`, and `conclusions.txt`. JSON preserves every validated final artifact/config hash, per-model arms and contrasts, both uncertainty scopes, terminal diagnostics, exclusions, missing blocks and limitations. The table always separates model seeds; the plain conclusions report numerical effects and conditional scope without automatically declaring a mechanism or success. `--require-complete` still writes an explicit incomplete report and exits with status 2 if the 45 planned runs are not all validated.

For the separate sensitivity:

```bash
python -m studies.revision.analyze_matched \
  --runs-root runs/revision/matched_grid \
  --output-dir output/revision/native-grid-analysis \
  --policy-seeds 0,1,2 --label native-grid --require-complete
```

The embedded independent synthetic checks use hand-calculable outcomes to detect best-policy selection, unpaired seed pooling, death-at-cap misclassification, incomplete-budget inclusion, mismatched starts and inconsistent saved scalar summaries. They also verify the exact two-policy bootstrap support and refuse a one-policy training-uncertainty interval. Production runs should be analyzed only after `experiment_design` syncs final configs, ledgers, episode arrays and start arrays to the corresponding local run directory.
